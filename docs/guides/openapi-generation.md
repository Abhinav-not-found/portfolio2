# OpenAPI Generation

## Overview

This project uses OpenAPI to maintain a single, shared contract between the backend API and the frontend applications.

The backend (`apps/server`) is responsible for implementing the API and defining its OpenAPI documentation. The OpenAPI specification is generated from the API documentation in the server source code.

The generated specification is stored in `packages/api/openapi.json`. This specification is then used to generate a reusable Axios API client inside `packages/api/generated/client/`.

Both the public client application and the admin application can consume this generated client instead of manually writing API request functions and duplicating API types.

---

## Architecture

The API generation flow is:

```text
apps/server
    │
    │ API implementation + OpenAPI documentation
    ▼
packages/api/openapi.json
    │
    │ openapi-typescript-codegen
    ▼
packages/api/generated/client/
    │
    ├───────────────┐
    ▼               ▼
apps/client     apps/admin
```

### Responsibilities

| Location                         | Responsibility                                           |
| -------------------------------- | -------------------------------------------------------- |
| `apps/server`                    | Implements the API and defines its OpenAPI documentation |
| `packages/api/openapi.json`      | Stores the generated OpenAPI specification               |
| `packages/api/generated/client/` | Stores the generated Axios API client                    |
| `apps/client`                    | Consumes the generated API client                        |
| `apps/admin`                     | Consumes the generated API client                        |

The backend is the **source of truth** for the API.

The generated files are outputs of the API generation process and should not be treated as manually maintained source code.

---

## Tools

The OpenAPI generation workflow uses the following tools:

### `swagger-jsdoc`

`swagger-jsdoc` scans the server source files for OpenAPI documentation written alongside the API routes and generates an OpenAPI specification.

For example, an API route can contain OpenAPI documentation describing:

* endpoint path
* HTTP method
* tags
* request parameters
* request body
* response structure
* status codes
* schemas
* examples

The resulting specification is represented as a JavaScript object and written to `packages/api/openapi.json`.

### `openapi-typescript-codegen`

`openapi-typescript-codegen` takes the generated OpenAPI specification and generates a typed API client.

This project generates the client using Axios:

```bash
openapi \
  --input ../../packages/api/openapi.json \
  --output ../../packages/api/generated/client \
  --client axios
```

The generated client contains the API models, services, request handling, and supporting code required to communicate with the backend.

## Generation

API generation is performed from `apps/server`.

### Generate OpenAPI specification

```bash
pnpm run generate:openapi
```

This runs:

```text
apps/server/src/scripts/generate-openapi.ts
```

The script loads the OpenAPI specification generated by `swagger-jsdoc` and writes it to:

```text
packages/api/openapi.json
```

### Generate API client

```bash
pnpm run generate:client
```

This performs both steps:

```text
1. Generate OpenAPI specification
              ↓
2. Generate Axios client
```

The generated client is written to:

```text
packages/api/generated/client/
```

Therefore, `generate:client` should normally be used after making API changes.

---

## Generated Files

The generation process produces two important outputs.

### OpenAPI specification

```text
packages/api/openapi.json
```

This is the machine-readable description of the backend API.

It describes the available endpoints, requests, responses, schemas, and other API metadata.

### Generated API client

```text
packages/api/generated/client/
```

This directory contains the generated Axios client.

Its exact internal structure is controlled by `openapi-typescript-codegen` and should not be manually reorganized.

## How It Works

The complete process is:

### 1. Define the API

An API endpoint is implemented in:

```text
apps/server/src/
```

The route is accompanied by OpenAPI documentation.

For example:

```text
Route implementation
        +
OpenAPI documentation
        ↓
swagger-jsdoc
```

### 2. Generate the OpenAPI specification

Running:

```bash
pnpm run generate:openapi
```

generates:

```text
packages/api/openapi.json
```

### 3. Generate the API client

Running:

```bash
pnpm run generate:client
```

passes the generated specification to `openapi-typescript-codegen`.

The generator creates:

```text
packages/api/generated/client/
```

using Axios as the HTTP client.

### 4. Consume the generated client

The generated client can then be shared by:

```text
apps/client
apps/admin
```

This prevents each application from independently defining API request functions, request types, and response types.

---

## Consuming the Client

The generated client belongs to the shared `@portfolio2/api` package.

Frontend applications should consume the generated client through this package rather than importing generated files using relative paths.

Conceptually:

```text
apps/client
      │
      │
      ▼
@portfolio2/api
      │
      ▼
generated/client
```

The same applies to:

```text
apps/admin
      │
      ▼
@portfolio2/api
```

This keeps the generated API implementation centralized and makes it possible for both applications to use the same API contract.

## Updating an API

When modifying an existing API or adding a new endpoint, follow this workflow:

```text
1. Update the API implementation
        ↓
2. Update/add OpenAPI documentation
        ↓
3. Run generate:client
        ↓
4. Review generated changes
        ↓
5. Use the updated client in frontend applications
```

For example:

```bash
cd apps/server

pnpm run generate:client
```

After generation, check:

```text
packages/api/openapi.json
packages/api/generated/client/
```

to ensure the new API changes are reflected.

## Important Rules

### 1. Do not manually edit `openapi.json`

`packages/api/openapi.json` is generated from the server's OpenAPI documentation.

Changes should be made in the server source code and then regenerated.

```text
❌ Edit openapi.json directly

✅ Update server API/OpenAPI documentation
   ↓
   regenerate
```

### 2. Do not manually edit generated client files

Files inside:

```text
packages/api/generated/client/
```

are generated artifacts.

Any manual changes will be overwritten the next time the client is generated.

```text
❌ Modify generated client manually

✅ Modify the API/OpenAPI definition
   ↓
   regenerate the client
```

### 3. The server is the source of truth

API definitions should originate from:

```text
apps/server
```

The generated specification and client are derived from the server.

### 4. Regenerate after API changes

Whenever an API endpoint, request, response, schema, or OpenAPI definition changes, regenerate the client:

```bash
pnpm run generate:client
```

### 5. Do not duplicate API definitions in frontend applications

Frontend applications should not independently recreate API types or request implementations when the generated client already provides them.

The goal is:

```text
One API definition
       ↓
One OpenAPI specification
       ↓
One generated client
       ↓
Multiple consumers
```

---

## Recommended Workflow

During development, the normal workflow should be:

```bash
# 1. Make API changes
# apps/server/...

# 2. Generate the OpenAPI specification and client
pnpm run generate:client

# 3. Use the generated client
# apps/client/...
# apps/admin/...
```

If only the OpenAPI specification needs to be regenerated without generating the client:

```bash
pnpm run generate:openapi
```

In normal development, prefer:

```bash
pnpm run generate:client
```

because it keeps both the specification and generated client synchronized.
